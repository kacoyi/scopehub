# ScopeHub contributor guidance

Follow applicable shared policies in `AGENTS.md` files in the checkout's ancestor directories. Project requirements and the engineering contract remain authoritative for ScopeHub.

## Language

- Use English for repository content, including documentation, specifications, source comments, new identifiers, commit messages, and GitHub issues and pull requests.
- Write user-facing translations and their locale-specific test expectations in the target language.
- Keep protocol identifiers, file paths, and technical names consistent with the engineering contract.
- Communicate with the project owner in Chinese unless they request another language. This conversation preference does not change the repository language.

## Project status

Follow `engineering-contract-v1.json` and `contracts/contract.json`. The scaffold includes an opt-in synthetic chart with frozen history, finite playback and separate freshness, coverage and connection indicators. Use `project/tasks.json` for current acceptance of the three-instrument workflow, interruption recovery, local imports and physical Windows experience. Keep unimplemented operations and unverified Windows acceptance explicit. Real data and cloud models are not configured. The product includes no data, AI, information or other financial service subscription by default. Implement the corresponding product capabilities; users can connect their own local data, APIs, paid services and custom adapters. Unconfigured defaults must not be interpreted as removing those capabilities. Owner files are development samples; explicit synthetic demos must remain distinguishable from user-configured local/API sources.

## Product intent

- Build for close human–AI financial collaboration: market understanding, analysis, decision-making, and authorized operations. Stocks and futures are the initial asset classes, with room for additional types.
- Select features and complexity for concrete collaboration needs. A lightweight footprint is not a mandatory objective; avoid unnecessary features and speculative infrastructure.
- V1 requires a workbench that users can compose from a blank canvas, reshape with the embedded AI and reopen with their data bindings. Users choose what appears, when, in what form and with which authorized interactions. Deliver the chart default alongside it. Select the renderer from native prototype evidence under ADR 0027 and verify the product with the separate chart-free release gate.
- Product AI should actively investigate, compute, challenge assumptions, and perform authorized operations. Human ownership of investment judgments does not imply a guarantee of profit or an independent capital-management mandate for the AI.
- For the product AI, acceptance of market risk grants no additional permissions. Keep investment judgment, operation authorization, and system correctness distinct; data and execution defects remain engineering failures to prevent and correct.

## Execution

- Start with `pnpm project:status --overview` for current scope, verification and the first follow-through. Use `pnpm project:status` for all review lanes and `--detail` for plans and individual evidence receipts. Use `project/tasks.json` for task scope, dependencies, acceptance and the next action. Maintain meaningful work items and update the focus before handing off; do not rely on conversation memory alone. For a read-only review with the pinned environment already installed, start with `./.venv/bin/python -B scripts/project.py status --overview --read-only` on POSIX or `./.venv/Scripts/python.exe -B scripts/project.py status --overview --read-only` on Windows. Its local navigation uses that same interpreter and leaves the environment and cache untouched.
- Use `pnpm project:brief` for derived product scope, implemented operations and capability delivery. Use `pnpm project:context [task-id]` for focused implementation entries, effective decisions, scenarios, risks and checks; `--detail` expands history and policies, and `--phase verify|handoff` selects finishing guidance. Read a referenced JSON section with `pnpm project:source <path> <json-pointer>`. Inspect actual implementation; these views are indexes, not new sources of truth.
- Before activating meaningful work, add its `plan`: observable outcome, change types, relevant context, hypotheses, failure risks with checks and recovery direction. Keep routine edits within the current task. Choose a small demonstrable slice and investigate consequential uncertainty early. Revise unfinished plans when evidence changes; preserve accepted history.
- `project/delivery.json` maps product scenarios and change types to checks. Use `project/feedback.json` for consequential defects, failed assumptions and feedback requiring follow-up. Treat suggestions as evidence under `project/development.json#/quality/feedback_loop`. Retain regression evidence for confirmed defects and the rationale for consequential product decisions. Do not invent user validation or count a scenario definition as observed behavior.
- `project/checks.json` is the harness catalog and acceptance mapping. Register implemented checks there as features arrive; planned and blocked checks never count as passed.
- Archive passing task evidence with `pnpm project:record <task-id> --report <report-path>`, attach the returned path and digest to the task, then mark it done. Completed task definitions and accepted ADR rationale are historical records; use new tasks or superseding ADRs for changed outcomes or decisions. See ADR 0004 for scope and lifecycle requirements.
- Use `diagnostic_reports` on tasks or feedback that refer to a retained diagnostic. Derive its `run_id`, `source_commit` and `report_sha256` with `pnpm project:diagnostic identify <report>`. An accompanying logical path such as `archives/runs/<run-id>/test-report.json` must match the recorded run. Checkout-local report references remain relative to the checkout. Ordinary checks and status do not consult the archive. Before removing temporary review outputs referenced by feedback, retain the original observations, verify their digests and update the source to its durable logical path.
- Resolve a diagnostic explicitly with `pnpm project:diagnostic resolve <run-id> <source-commit> <report-sha256> --archive-root <path>`. The optional host setting `SCOPEHUB_ARCHIVE_ROOT` points to the development storage root's `archives` directory. The resolver verifies original bytes, associated logs and any report-bound session or field observation artifacts before returning the recorded outcome. Field observations can be kept under the archived run or under the archive root’s observations directory. Resolving a diagnostic creates no acceptance receipt.
- Use `uv sync --locked` and `pnpm install --frozen-lockfile` for setup with Python 3.12, Node 24 and the pinned pnpm version. After moving a checkout between machines, set aside copied `.venv`, `node_modules` (including workspace packages) and Cargo `target` directories before rebuilding on the new host. Preserve `.reports` for prior diagnostics and evidence.
- Run `pnpm check` for the local harness. Reports and logs are retained under `.reports/runs/<run-id>` with a latest copy at `.reports/test-report.json`; `pnpm project:status` reports whether the latest result matches current execution inputs. A blocked check is not a pass. Native Windows validation is required for M0 completion.
- Use `pnpm project:storage` or `python3 -I -S scripts/storage.py` for a read-only inventory of allocated Cargo target blocks in registered worktrees alongside the primary checkout and immediate registered members of the explicitly configured managed root. The inventory includes independently identified Cargo caches one level below `target/` in their parent total. Append `--collect` to collect idle Cargo debug intermediates when usage exceeds 64 GiB, stopping at 32 GiB or when eligible caches run out. Local checks and successful Herdr launches apply the same policy with a 30-second best-effort budget. Set `SCOPEHUB_STORAGE=off` to skip automatic maintenance. Collection requires the host Linux process and lock namespace and a supported local filesystem. With partial process visibility, collection is limited to locked completed incremental sessions and single-link dependency files at least 24 hours old with exclusive kernel leases. Executable candidates must have a matching Cargo test fingerprint and pass Linux's executing-file guard. The read-only estimate precedes lock and lease acquisition. Normal binaries, shared libraries, examples, release builds and evidence stay protected.
- Local verification subprocesses default to `CARGO_INCREMENTAL=0` unless explicitly set. Interactive Cargo and hosted verification use their own environment.
- Start with the affected test or runnable product interaction. Use `pnpm project:doctor` for toolchain diagnostics, `pnpm project:impact [--base <ref>]` to preview coverage, `pnpm check:changed [--base <ref>]` for affected checks and `pnpm check:fast` for broader feedback. Use `pnpm check --task <id>` for the task's required checks plus environment and project validation. Select profiles for the coverage they add. Archive the required checks on matching inputs from local or hosted verification before marking work done. Selected checks report every omission. Retain the failed report when changing direction. Use `uv run python` for repository Python commands.
- Apply `project/delivery.json#/source_control/verification` to each independently usable outcome. Start with its shortest runnable interaction. Batch native and hosted task checks on the reviewed candidate. While CI runs, dispatch independent ready work. At handoff, use the timing escalation in `project/delivery.json#/source_control/scaling` to assign repeated budget overruns and check their measured recovery.
- Follow `project/delivery.json` `scaffold_maintenance` when checks or workflow commands fail, observed behavior escapes passing checks, or the current task exposes a concrete capability gap. During authorized development, investigate and make ordinary local repairs or extensions proactively; preserve the interrupted task, add a regression, validate closure and resume delivery. Do not retry unchanged failures blindly or weaken checks to obtain a pass. At session start and handoff, triage the retained failures in project:status, feedback needing assignment, and weekly regressions in project:ci. The active development AI owns follow-through. Record newly confirmed consequential feedback before its regression run so completion evidence binds the observed defect. At intake, assign its regression checks to corrective tasks. Include the checks for open major or critical findings in the affected active task’s existing risk plan. Start with a valid and rejected case at the first product or verification entry capable of observing the distinction. Local project checks compare feedback against HEAD and the common ancestor with the locally tracked protected branch before expensive verification. SCOPEHUB_REVIEW_BASE and SCOPEHUB_CHECKPOINT_BASE can supply specific local review or checkpoint revisions.
- Use `pnpm project:recover --task <interrupted-task-id> --save` to retain diagnostics and original control files. When normal commands cannot start, use `.venv/bin/python -S scripts/recovery.py --save` on POSIX or `.venv\Scripts\python.exe -S scripts\recovery.py --save` on Windows. If the virtual environment is missing or the command produces no JSON snapshot path, open a shell outside it and use a working host Python 3.9 or newer. Run `python3 -I -S scripts/recovery.py --save` on POSIX or `python -I -S scripts\recovery.py --save` on Windows. These commands collect a standard-library diagnostic. Restore the pinned environment for normal checks. If damaged records prevent task creation, preserve the failure, make the minimal bootstrap repair, then restore validation and backfill task/feedback records before broader work or completion.
- Follow `project/delivery.json` source-control policy. Commit coherent validated outcomes, recovery checkpoints and handoffs on a task branch. Use `pnpm project:checkpoint` to inspect recoverability, local upstream refs and check timings. A local commit, remote push, CI pass, task completion, merge and release establish different states.
- Use `pnpm project:timing` for retained timing comparisons and `--recent` or `--run <id>` for explicit hosted inspection with the pinned GitHub account. Follow the dated weekly review and regression actions in `project/delivery.json`.
- Within owner-authorized publication scope, push meaningful checkpoints and create or update a draft PR; an ordinary task-branch push without a PR does not trigger the current workflow. Do not ask again for permission already granted for that repository and branch scope. Initial upload of previously local content to a public remote still needs publication authorization when none exists.
- Use `pnpm project:ci` to inspect the latest workflow for the current clean commit with the official `gh` account workflow. Missing, queued, cancelled, stale and failed runs are not passes. Continue independent work while CI runs, then revisit failures and the current commit before integration. Do not merge or release solely because a branch was pushed.
- Use one short-lived task branch and draft PR per independently verifiable outcome. Apply the internal GitHub delegation in `project/delivery.json#/source_control/authorization`. External Issues and third-party submissions are outside the owner's current intake. Before merging a stacked branch, resolve its dependent PRs. Verify main CI and automatic head cleanup after the merge.
- Run `pnpm project:branches` after integration and when the weekly review comes due in `pnpm project:status`. Check each open PR base and head, protection, exact ancestry and recoverability before retiring a ref. The periodic list in `project/delivery.json#/scaffold_maintenance/periodic_reviews` also covers worktrees, evidence and compatibility. Advance a review date only after recording its findings and follow-up.
- After completing a coherent delivery and archiving its evidence, run `pnpm project:integration --pr <number>` and present the integration recommendation at handoff; do not wait for future milestones. This read-only check observes the live PR, head/base, required jobs, protection and completed task scope. Review the actual diff and obtain or reuse applicable owner merge authorization separately; inspect again immediately before execution and bind the merge to the expected head. Verify the resulting main commit and its CI afterward.
- Download observed CI artifacts into `.reports/ci/<run-id>/<platform>` and archive with `pnpm project:record <task-id> --report <artifact-dir>/test-report.json --artifact-root <artifact-dir>`. Do not overwrite local latest reports. Import checks source and task/decision identity, CI provenance and log digests; authenticated artifact retrieval remains the trust boundary.
- Run `pnpm project:history --base <reviewed-commit>` when a review base is available. CI compares accepted tasks and ADRs against the PR base or previous pushed revision. A missing base is reported as not applicable, never as a completed comparison. The local uncommitted state is not recoverable Git history.
- `pnpm project:readiness` exposes remaining scenario, milestone, release and unresolved-feedback gates. A clean committed source, actual packaged Windows acceptance, retained artifacts and owner product review are release requirements. Fast checks, compilation and mock evaluation each establish only their own scope.
- Follow `project/delivery.json` release lifecycle when a usable version or material fix reaches main: identify the candidate, test and retain its exact packaged bytes, present the release proposal, publish within applicable owner authorization, then verify downloaded artifacts. A technical readiness result does not grant publication permission. Preserve failed candidates and use reviewed repair/revert work; data migration recovery needs its own tested procedure.
- Expensive packaged acceptance uses `pnpm check --profile release --require-windows` or the CI manual `release` profile. Checks with `cadence: release` are omitted from the default change harness and remain visibly unverified. Run a check explicitly through the affected task when a dependency or packaging change needs it sooner. Do not require a two-hour soak test for every ordinary edit.
- Edit canonical JSON Schemas in `contracts/schemas/protocol.schema.json`; run `pnpm generate`. Never edit generated types or operation schema projections. Add shared valid/invalid vectors when the wire contract changes.
- Follow dependency boundaries checked by `scripts/check_architecture.py`. Add implementation modules when a use case needs them, not as placeholders.
- Choose external data channels, products, services, libraries, shared capabilities, or local code by concrete fit and lifetime cost. Reuse suitable capabilities; build focused implementations when existing options are unsuitable or more burdensome. Keep integrations replaceable and evaluation proportional to their impact.
- Keep information channels independently replaceable and able to coexist. Omniscience is an optional candidate; no named provider is a mandatory gateway. Preserve source provenance and capability differences, and add adapters when a concrete workflow needs them.
- AI tools and user actions must share the Rust operation registry. Schema availability does not grant permission or mean an operation is implemented.
- Keep repository content in English and owner communication in Chinese. Store decisions and status as JSON; do not add prose guides or README files. Preserve legally required licenses and notices.
- The development AI owns technical planning, architecture choices, implementation, verification and maintenance under ADR 0007. Record consequential technical evolution with an ADR and appropriate compatibility checks; consult the owner about product behavior/scope, user-data consequences, costs, external transmission or permission changes. Reuse existing authorization. Ordinary technical decisions do not require the owner to select an implementation.
- No trading, real provider scraping, cloud model calls, generated Python execution, or credential handling is part of M0. Apply the parent `ai-cap` rule when a later task actually uses shared capabilities.

## Development collaboration and code quality

- Keep new task and integration checkouts under one dedicated root outside Git checkouts. The coordinator sets the shared repository-local value with `git config --local scopehub.worktreeRoot "$HOME/worktrees/scopehub"`. The creation command defaults to that home-relative location when the key is absent. Worktrees and ordinary builds can use the source filesystem, with optional archive storage configured separately.
- Use `pnpm project:worktree create <name> --branch <local-branch>` for an existing branch or `pnpm project:worktree create <name> --new-branch <local-branch> --base <commit-ish>` for a new one. Use an explicit reviewed ref or commit as the integration base. Repeating a matching creation request preserves working changes. Use `pnpm project:worktree list` to locate registered checkouts, including existing legacy paths. `pnpm -s project:worktree use <name>` prints the managed checkout path. Open a separate terminal there to work or launch Herdr.
- After an interrupted creation, let Git finish and inspect `git worktree list --porcelain`. Retry the same request for a completed checkout. If Git created only the branch, verify its tip against the intended base before retrying with `--branch`. Preserve an incomplete checkout for inspection and use a different name and branch to resume other work. Keep the persistent lock file in the Git common directory so every invocation coordinates through the same file.
- For use from older branches, save `git show <reviewed-commit>:scripts/worktree.py` to a commit-specific file outside the checkouts. The coordinator can register `git config --local alias.scopehub-worktree '!python3 -I -S "/absolute/path/to/pinned/worktree.py"'` using that file and the available host Python. Then use `git scopehub-worktree create|use|list` from any checkout of the repository. To run pinned retirement with the project's Python 3.12, keep `worktree_retirement.py`, `storage.py` and `operational_paths.py` from the same commit beside `worktree.py`.
- Before retiring a task worktree, finish or preserve dirty work and hand off any active Herdr session. Archive required evidence through the project evidence workflow and preserve any needed files under `.reports` outside the checkout. Confirm the checkout is clean and idle, then run `git worktree remove <path>` from another checkout. Keep branch and commit references as required for recovery and integration.
- Use `pnpm project:worktree retirement` for a read-only observation of registered checkouts before reviewing removal. Use `--archive-root <path>` or `SCOPEHUB_ARCHIVE_ROOT` to verify independently retained files. The archive can mirror checkout-relative files under `worktrees/<head>/files/` and native diagnostic runs under `runs/` or `recovery/`. The report checks integration against the locally observed `origin/main` tip, or a committed exact-head disposition supplied with `--dispositions <commit>:<path>`. The disposition document has `version: 1` and a `dispositions` array with `head`, `disposition` (`abandoned` or `superseded`), `reason` and `recoverable_ref` for each entry. The report verifies that worktree-private Git objects remain reachable through shared references. A row with `review_intake: true` is held solely for partial host process visibility and is available for human review. A `candidate` has no observed holds. Re-run the report immediately before separately authorized removal because commits, files and activity can change.
- For a retirement inventory that exhausts its default of 20,000 entries, supply `--entry-limit <count>` with an integer from 1 through 200,000. The same limit applies per checkout to each ignored-path inventory and the Python consumer inventory. An exhausted scan remains a hold.
- In the owner's current workflow, the owner opens Codex CLI in a local Herdr window. AI agents fill all engineering roles, including implementation, review and coordination. From a coordinator terminal on supported local Linux, use `pnpm project:herdr <task-id> implement --assignment "<scope>" --space <id>` to open a visible owned assignment with automatic collection and retirement. Use `review` with `--source <full-clean-commit>` for an owned review, or `coordinate` for a coordinator. Use `--standalone` for a deliberately interactive session. Launches without a matching local parent or a visible space keep standalone behavior unless explicitly registered. The development AI chooses tabs, model roles, worktrees, installation of needed development tools and the next ready task. Hand off when the owner needs to supply a concrete input or accept a demonstrated result. Use the role defaults in `project/development.json#/herdr`. Raise reasoning with `--effort` or select the supervision family for one implementation with `--escalate-model` when correctness warrants it. Include the reason in the assignment.
- The owner and development AI co-create ScopeHub. In product requirements, "user" means any ScopeHub user. Keep every user's private product records local to their profile. Use the connected model for ordinary turns within the disclosed scope. A saved private excerpt leaves the device only when that user selects its preview for that request and recipient. Use synthetic content in development and CI.
- `project/development.json` defines owner/development-AI responsibilities, module ownership, allowed dependencies, public entries, capability delivery and quality review. This development relationship does not specify interactions between product users and the embedded AI. Do not convert owner development preferences into product runtime requirements.
- The owner defines product needs, experience preferences and product tradeoffs. The development AI synthesizes requirements, asks concrete behavior questions when needed, makes engineering choices and closes the implementation/verification/feedback loop. Refine nearby work; do not demand an exhaustive product-AI feature inventory before development.
- Every newly active task needs `plan.implementation` (modules, existing entrypoints, authoritative rule references, non-goals and open questions) and `plan.evolution` (preserved/changed behavior, data handling and cleanup). Keep historical tasks immutable and refine unfinished tasks as evidence changes.
- Task `delivery` defaults to `current-contract`; explicitly classified `later` work stays visible without silently expanding the current release. Preserve existing requirements and record owner scope decisions before moving required work out of the current contract. This classification is part of task verification identity.
- Group logic by responsibility and reason to change; expose narrow public operations and hide internal classes, vendor SDKs, storage and processing details. Use the declared module dependencies and public entries; add abstractions for concrete needs. Architecture checks cover declared dependencies and statically visible imports, not complete design quality.
- Assign business state and invariants to clear owners. The application authorizes and coordinates; domain logic maintains domain invariants; persistence executes transactional storage through the core single-writer path. UI and workers never write the application database.
- Protect domain rules with independent expected values, module collaboration with contract checks and critical journeys with integrated behavior. Review boundary, failure, cancellation and recovery behavior in proportion to risk. Avoid tests that only mirror implementation and do not treat successful builds as usability acceptance.
- From the first implementation, weigh the cost of refactoring or rewriting a design alongside its fit for today's workflow. Apply `project/development.json#/quality/evolution` when choosing or revisiting consequential designs.
- Use direct refactoring or staged replacement according to actual change risk. State preserved behavior, changed requirements, data migration/recovery and compatibility exit criteria. Verify cutover and remove obsolete paths; persistent changes require versioned tested migrations and recovery, not an assumed safe downgrade.
- Before completion review cohesion, dependencies, public surface, data ownership, failure cleanup, regression evidence and transition removal. Record observed owner feedback separately from engineering checks. `project:status` explains historical receipts and latest omissions; historical evidence never becomes current or release acceptance merely because it is displayed.
