# ScopeHub contributor guidance

Read the applicable ancestor `AGENTS.md` files. Follow `engineering-contract-v1.json` and `contracts/contract.json`. Write repository content in English and user-facing translations and their test expectations in the target language. Speak Chinese with the owner unless asked otherwise. Use the contract's technical names. Keep decisions and status in JSON, avoid additional prose guides or READMEs, and preserve required licenses and notices.

## Start a product task

1. Run `pnpm project:status --overview`, then `pnpm project:context <task-id>`. Use `pnpm project:brief` for delivered capabilities and `pnpm project:source <path> <json-pointer>` to follow authoritative rules. Use `--detail` for the full records and `--phase verify|handoff` at those stages. For a read-only review in an installed environment, start with `./.venv/bin/python -B scripts/project.py status --overview --read-only` (Windows `./.venv/Scripts/python.exe`). Follow its pinned-interpreter links.
2. Read the task scope, direct findings, and shared product history in ordinary implementation context. Follow the historical record to its observation, original evidence and consumer check. Confirm which code was involved. Inspect the actual implementation and the relevant scenario in `project/delivery.json#/scenarios`.
3. Follow the first-test rule in `engineering-contract-v1.json#/implementation_policy/first_test`. Exercise the shortest real interaction with valid input and the rejected or interrupted case at the earliest entry that can tell them apart. Use independent expected financial values and check that the last accepted state survives. Run `pnpm check --task <id>` before handoff and inspect omissions.
4. Keep the active task and its next action current in `project/tasks.json`. Before activation record an observable slice, change types, context, hypotheses, risks with checks, and rollback. Include `plan.implementation` (modules, entries, rules, non-goals and open questions) and `plan.evolution` (preserved and changed behavior, data handling and cleanup). Keep completed definitions and accepted ADRs intact under ADR 0004. `delivery` defaults to `current-contract`. Record owner decisions before moving required work to `later`, since classification is part of verification identity.

## Product boundaries to check first

- Start with what the user can do. ScopeHub brings people and AI together to investigate markets, compute, challenge assumptions, decide and perform authorized operations. Stocks and futures come first. V1 pairs a chart default with a workbench users can compose from blank, reshape with AI and reopen with their data bindings. Users choose presentation, timing and authorized interactions. Follow ADR 0027 for the native renderer qualification and `project/delivery.json#/release_policy/required_checks` for the independent chart-free gate.
- Follow `engineering-contract-v1.json#/domain` for dataset and instrument identity, bar invariants, continuous futures, snapshots, stream handoff and market quality. Preserve units, timestamp and trading-day semantics, unknown volume, source provenance and separate freshness, coverage and connection signals. Follow `contracts/market-data-v1.json#/onboarding` for local/API import, preview, rights and refresh. Keep independently replaceable sources and their different capabilities. Omniscience is an optional candidate.
- Startup includes no bundled data, AI, information or financial service subscription. Implement user-supplied local data, APIs, paid services and custom adapters under `engineering-contract-v1.json#/product/service_policy`. Real data and cloud models are unconfigured. Owner files are development samples. Keep the opt-in synthetic chart's frozen history, finite playback and labeling distinct from configured sources. Read `project/tasks.json` for observed acceptance of the three-instrument workflow, interruptions, imports and physical Windows use.
- Follow `contracts/worker-runtime-v1.json#/runtime/cancellation` and `contracts/worker-runtime-v1.json#/protocol/error_handling` for request ownership, late or duplicate terminal replies, retries and errors. Exercise cancellation, refusal and recovery through the affected consumer, including whether a committed action can be recovered after a failed follow-up read.
- AI tools and user actions share the Rust operation registry. Check implemented operations, grants, confirmation and replay in `contracts/contract.json` and `engineering-contract-v1.json#/authorization`. Market risk, operation authority and engineering correctness are separate. People own investment judgment. The product AI has no independent capital-management mandate or profit guarantee. M0 excludes trading, real provider scraping, cloud model calls, generated Python execution and credential handling.
- Keep each user's private records local to their profile. Ordinary turns use the connected model within the disclosed scope. A saved private excerpt leaves the device only after that user selects its preview for that request and recipient. Use synthetic content in development and CI. See `contracts/storage-v1.json#/private_content` and the product AI rules under `engineering-contract-v1.json#/ai`. In product requirements, “user” refers to any product user.

## Implementation and verification

- `project/development.json#/modules` and `/data_ownership` define ownership and public entries. Application code authorizes and coordinates, domain code maintains invariants, and persistence writes transactionally through the core single writer. Keep database writes out of UI and workers. Follow `scripts/check_architecture.py` and `project/development.json#/quality` for boundaries, verification, evolution and final review. Add modules or abstractions for concrete needs. Use versioned, tested migration and recovery for persistent changes. Verify cutover and remove obsolete paths.
- The development AI owns technical planning, design, verification and maintenance under ADR 0007. Record consequential changes with an ADR and compatibility checks. Follow `project/development.json#/collaboration` for owner decisions on product experience, data, costs, transmission and permissions. Record observed owner feedback separately from engineering evidence. The development relationship is separate from product AI behavior.
- Change wire definitions in `contracts/schemas/protocol.schema.json`, run `pnpm generate` and add shared valid and invalid vectors. Generated types and operation projections come from the generator. Use `engineering-contract-v1.json#/implementation_policy/build_or_reuse` for dependencies and integrations.
- Use `uv sync --locked` and `pnpm install --frozen-lockfile` with Python 3.12, Node 24 and pinned pnpm. Use `uv run python` for repository Python. After moving machines, set aside copied `.venv`, all `node_modules` and Cargo `target` directories before rebuilding. Preserve `.reports`. Local harness subprocesses default to `CARGO_INCREMENTAL=0`. Interactive Cargo and hosted verification use their own environment.
- Use `pnpm project:doctor` for setup, `pnpm project:impact [--base <ref>]` to preview selection, `pnpm check:changed [--base <ref>]` or `pnpm check:fast` for early feedback, and `pnpm check` for the full local change harness. `project/checks.json` owns the check catalog and acceptance bindings. Register newly implemented checks there. `project:status` compares current inputs with `.reports/test-report.json`. Original logs and reports are in `.reports/runs/<run-id>`. Blocked and omitted checks remain unverified. M0 completion requires native Windows validation.
- Follow `project/delivery.json#/scaffold_maintenance` and `project/development.json#/quality/feedback_loop` for defects, failed assumptions, missing capabilities and work interruptions. At startup and handoff triage retained failures, unassigned feedback and weekly CI regressions. Keep the failed report. Record consequential observations in `project/feedback.json` before running the regression, assign checks to corrective work, and include open major or critical regressions in the active task's risk plan. Diagnose, repair within scope, verify, and resume. For a normal recovery use `pnpm project:recover --task <id> --save`. If it cannot start, follow the exact fallback commands and minimal-repair order in `project/delivery.json#/scaffold_maintenance/bootstrap`.
- Archive matching required checks with `pnpm project:record <id> --report <report-path>`, then attach its path and digest before marking done. Use `pnpm project:history --base <reviewed-commit>` when a base is available. `SCOPEHUB_REVIEW_BASE` and `SCOPEHUB_CHECKPOINT_BASE` can pin local comparisons. A missing base leaves the comparison unverified.
- For retained diagnostics use `diagnostic_reports` and derive the locator with `pnpm project:diagnostic identify <report>`. A logical archive path must agree with its run ID. Keep checkout-local paths relative. Before removing referenced temporary outputs, retain the originals, verify their digests and update the source to the durable path. Resolve explicitly with `pnpm project:diagnostic resolve <run-id> <source-commit> <report-sha256> --archive-root <path>` or `SCOPEHUB_ARCHIVE_ROOT` pointing to the developer archive's `archives` directory. The resolver checks original bytes, logs and bound session or field observations, including separate archived observations. It produces no acceptance receipt. Ordinary status and checks use checkout records.

## Coordination, integration and release

- Use one short-lived task branch and draft PR per independently verifiable outcome. Read `project/delivery.json#/source_control` for checkpoint, verification, authorization, and integration. Use `pnpm project:checkpoint` to inspect recoverability and timing. Commit coherent validated work and handoffs. Reuse applicable publication authorization for task branches and draft PRs. Initial public upload outside that grant needs owner authorization. External issues and third-party submissions are out of scope.
- Use `pnpm project:ci` for the latest matching workflow and weekly observations with the pinned official `gh` account. Ordinary task-branch pushes need a PR to trigger the workflow. While checks run, continue independent ready work. Use `pnpm project:timing` to inspect retained timing or add `--recent` or `--run <id>` for hosted measurements. Follow `project/delivery.json#/source_control/scaling` for repeated overruns and measured recovery. Import observed artifacts from `.reports/ci/<run-id>/<platform>` using `project:record --report <artifact-dir>/test-report.json --artifact-root <artifact-dir>`. Keep the local latest report intact.
- After coherent delivery and evidence, run `pnpm project:integration --pr <number>` and present its recommendation without waiting for unrelated milestones. Apply the diff review, live protection, merge authorization and expected-head procedure in `project/delivery.json#/source_control/integration`. Verify dependent PR bases before merging stacked work and verify main CI and head cleanup afterward. Use `pnpm project:branches` after integration and when due. Advance periodic review dates only with recorded findings and follow-up under `project/delivery.json#/scaffold_maintenance/periodic_reviews`.
- Use `pnpm project:readiness` and `project/delivery.json#/release_policy/lifecycle` for material changes on main, exact candidate bytes, packaged Windows acceptance, owner product review, publication authorization and downloaded-artifact validation. The expensive path is `pnpm check --profile release --require-windows` or the manual CI release profile. Change checks omit `cadence: release` unless explicitly selected through affected task coverage. Preserve failed candidates and apply reviewed repair, revert or tested migration recovery.

## Local worktree and Herdr operations

- Keep task and integration checkouts under one dedicated root outside Git checkouts. The coordinator can set it with `git config --local scopehub.worktreeRoot "$HOME/worktrees/scopehub"`. That home-relative path is also the default. Use `pnpm project:worktree list`, `create --help` and `use <name>`. Create from an explicit reviewed base or reuse the branch's registered checkout. Open a separate terminal there. Keep ordinary builds on source storage and use the separate archive for retained evidence.
- If creation is interrupted, let Git finish and inspect `git worktree list --porcelain`. Retry the same request for a completed checkout. For a branch alone, verify its tip before retrying with `--branch`. Preserve an incomplete checkout and use another name and branch. Keep the creation lock in the common Git directory. For older branches save `git show <reviewed-commit>:scripts/worktree.py` outside the checkouts and register `git config --local alias.scopehub-worktree '!python3 -I -S "/absolute/path/to/pinned/worktree.py"'`. Pinned retirement uses project Python 3.12 and sibling `worktree_retirement.py`, `storage.py` and `operational_paths.py` from the same commit.
- Before removal, preserve dirty work, reachable refs and required evidence outside the checkout. Hand off active Herdr assignments. Use `pnpm project:worktree retirement --help` for archive, disposition and inventory limits. In `scripts/worktree_retirement.py`, see `retained` for archive layout, `read_dispositions` for exact-head records and `retirement_report` for holds. `review_intake` indicates partial process visibility as the sole hold. Re-run the read-only inventory immediately before authorized removal. Confirm a clean, idle checkout and run `git worktree remove <path>` from another checkout.
- Use `pnpm project:storage` or `python3 -I -S scripts/storage.py` for inventory. `--collect` applies the 64 GiB to 32 GiB policy to eligible idle Cargo debug intermediates. Local checks and successful Herdr launches apply the same policy with a 30-second best-effort budget. `SCOPEHUB_STORAGE=off` disables automatic maintenance. In `scripts/storage.py`, see `inspect_repository` for checkout and nested cache accounting, `collect_target` for process and filesystem requirements and `remove_intermediates` for protected files and locking.
- The owner starts Codex CLI in local Herdr. Development agents handle implementation, review and coordination. Follow `project/development.json#/herdr` for `pnpm project:herdr <task-id> implement --assignment "<scope>" --space <id>`, source-bound review, standalone or one-shot work, owned collection and role defaults. Explain a model escalation in the assignment. Hand off when the owner needs to supply an input or accept a demonstrated result.
